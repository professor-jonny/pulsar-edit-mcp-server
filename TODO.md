## Working on this project

- **Restarts:** every edit to a `lib/*.js` file (and the panel code in `lib/pulsar-edit-mcp-server.js`) needs a full Pulsar restart. There is no hot reload. `package.json` changes need a package reload. A brand-new standalone file needs nothing until something requires it. Tool registration or schema changes are only picked up by a new MCP session.
- **Method:** one change at a time. Write the test first (see it fail, then pass), run `node test/check.js` (syntax, module load under `test/atom-shim.js`, then `npm test`), restart Pulsar, then verify live with a real tool call before calling anything done. Prove a change on one tool before widening it to the others.
- **New tool or new stats key:** it must be added in three places or its counts silently vanish: the `editStats` initialiser and the `TOOL_REGISTRY` in `lib/edit-stats.js`, and a key in `GROUP_DEFS` in `lib/pulsar-edit-mcp-server.js`. `bump()` on a key that is not in the schema is a silent no-op.
- **Renaming or consolidating a tool:** grep `lib/*.js` for the old name as a string literal and as a table key. Keyed lookups fail silently.
- **Changelog:** add an entry to the top of CHANGELOG.md for every behaviour change.

### Design rules (settled, do not reopen without a strong reason)

- Engine defaults must be safe for destructive callers. Permissive behaviour is opt-in (for example `delete` opts out of `autoRescue`).
- An ambiguous match with no `occurrence` is refused, never guessed.
- `occurrence` counts matches from 1 and must be a whole number. An out-of-range value is refused, never clamped.
- Part-line editing exists only as `replace` with `fragment:true` (one line or a multi-line span that may start and end mid-line, since 2026-10-17), guarded by `lib/identifier-boundary.js`. The guard refuses (does not just warn); `guardIdentifier:false` is the escape hatch.
- Regex exists only in `sed` and in the search tools (`find-text`, `grep-file`, `grep-project`, `search-functions`); the edit tools take literal text only (R2a, closed 2026-10-30).
- Failure counters are tallied in parallel on purpose: a failure lands in the shared diagnosis key and in the tool's own key. All hints for all tools must be logged, and a match failure records the diff, the buffer text and the proposed text.
- Tools keep distinct, separately described names; only the implementation is shared. Do not collapse the tool surface into mega-tools with a mode parameter, and do not leave aliases for retired tools.

### R4 - `sed` as a JS implementation of GNU sed (decided by PJ 2026-10-18; the tool is done and live; R4g and R4k are MEDIUM, the other open items are LOW)
Goal: the `sed` tool behaves exactly like GNU sed 4.9: the same script syntax, POSIX BRE/ERE regex with leftmost-longest matching, replacement with `\1` and `&` (a literal `$` stays literal), and the same commands and addresses. Status: R4a to R4d are done and the tool has run real sed scripts since 2026-10-24 (see CHANGELOG.md); the old JS-regex subset (`lib/sed-plan.js`) was deleted on 2026-10-25. `sed` is the part-line regex tool, so the fragment-mode regex of R2a is not built (R2a keeps only its guard).

- Decisions: our own implementation in pure modules, no sed binary needed at runtime: `lib/posix-regex.js` (BRE and ERE with the GNU extensions, own matcher), `lib/sed-parse.js` (script parser), `lib/sed-run.js` (interpreter over a lines array). The test oracle is real GNU sed 4.9: Linux sed in the assistant's sandbox generates golden outputs, which the tests in `test/` embed and run in plain node; PJ's Windows sed 4.9 (`test/sed-oracle/sed.exe`, not part of the package) runs the differential checks (`test/sed-oracle/run-diff.js`).
- Never implemented: `e` (shell exec). Off by default behind a future capability gate: `w`, `W`, `r`, `R` (file I/O).
- Known tail risk, stated up front: POSIX submatch rules for highly ambiguous patterns. Differential tests measure it and every remaining deviation is listed in the CHANGELOG.
- Decided (2026-10-21 to 2026-10-24): exact GNU sed 4.9 semantics with no extra guards (a `sed -n -i` style script may empty the file, as real sed does); `dryRun` stays as the tool's own preview; the old engine was replaced outright, with no fallback; `occurrence` is only the picker for an ambiguous scope hint (`s///N` stays in the script); `w W r R e` are refused by the parser sandbox.

## 2. Failure handling and retry

**Why:** failures are frequent and each one makes the caller resend the whole call to fix one field. The commonest case is an ambiguous anchor, where the failure already lists the candidate lines and the fix is a single integer (`occurrence:N`).

**What exists:** `features.retryOnFail` in `lib/tool-framework.js` (stashes a failed call and merges one named field into a bare retry) plus `RETRY_FIELD_BY_TOOL` / `retryNudge()` in `lib/match-engine.js`. It works end to end with both relative and absolute paths, but only `replace` has it registered.

**Known inconsistencies:**
- Tools signal failure with five different flags (`matched:false`, `inserted:false`, `deleted:false`, `found:false`, `applied:false`), and some `deleted:false` / `applied:false` results are dry-run previews rather than failures. The framework can only stash on `matched:false`.
- `RETRY_FIELD_BY_TOOL` lists `delete`, `replace-block` and `replace-function-body`, but none of them has `retryOnFail` registered. Their "not found" messages can therefore advertise a bare retry the framework does not support (it works only as a fresh, complete call). `delete`'s Mode 4 paths already omit the nudge on purpose.

**Principles:** prove on one tool, restart, verify live, then widen. Unadvertised capability goes unused, so the failure text itself must say how to retry cheaply. Only retryable failures stash (a bad path or missing argument must not). Keep `matched:false` working alongside any new signal.

**Decisions already made:**
- A: a retry may supply any single anchor key and it replaces whichever anchor the original call used. A retry supplying two anchor keys is rejected.
- B: the new `retryable` signal is additive. The framework stashes on `retryable` or on the legacy `matched:false` path; `retryable` wins if both are present.
- C: occurrence retry is one-shot and only valid right after an ambiguity failure on the same file. With nothing pending, `{filePath, occurrence}` falls through to the normal ambiguity refusal.

**Proposed 2026-11-06, from PJ (design only, not decided, not built): one shared last-call stash for all tools.** Today retry is built per tool (`retryOnFail` on `replace`, `commitLastPreview` on `insert`, `confirm` on `apply-patch` and `replace-across-files`) and R4k step 3 would add a fourth, `again:true`, for the searches. Instead the framework would keep one stash per MCP session and tool, and any tool could be re-run by resending only the fields that change.
- P1 (policy by class): read-only tools (`grep-file`, `grep-project`, `find-text`, `search-functions`, and probably `read` and the `get-*` tools) stash EVERY call, hit or miss, because a replay is harmless and the file is read fresh. Write tools (`replace`, `insert`, `delete`, `replace-block`, `replace-function-body`, `sed`) stash FAILED calls only: a failed call wrote nothing, so a corrected resend cannot apply an edit twice, and a successful write is never stashed. This is what `retryOnFail` already does for writes, so the change is mainly to extend the stash to read-only tools.
- P2 (same session, same LLM): key each entry by MCP session ID and tool name, so two chats cannot replay each other's calls. The session ID identifies a connection, not the model (a model switch inside one chat keeps the stash), which is accepted; record the client name from the `initialize` handshake as a sanity check.
- P3 (timeout): every entry has a time to live. Proposed starting values, to be decided: a few minutes for write tools (a corrected retry follows the failure at once), about 30 minutes for read-only tools.
- P4 (invalidation): a write-tool entry is cleared by any edit to the same file, by this server or by PJ in the editor (compare the buffer's changed state or mtime with the value stored at stash time), because hints such as candidate line numbers go stale. An edit to a different file does not clear it. Read-only entries need no invalidation (session and TTL only).
- P5 (replay shape): the caller resends only the changed fields, for example `{filePath, caseSensitive:false}` or `{filePath, occurrence:2}`; decision A (one anchor key replaces the original anchor, two are rejected) still applies. Every replayed reply echoes the effective arguments so a wrong slot is visible. An empty or expired slot gives a clear error, and a replay that would leave a required field unset falls through to the normal validation error.
- P6 (schema, OPEN): required fields (`query`, `filePath`, `old_str`, `new_str`) are rejected by the Zod schema before the handler runs (the transport gotcha in F3). Two options: make them optional with a handler check (the `commitLastPreview` pattern), or add one generic `replay` tool that merges overrides into the session's last call and validates the result against the target tool's own schema (no schema change per tool and no new parameter in every tool list; but it cuts across the rule against a tool with a mode parameter, which PJ must decide).
- P7 (OPEN numbers): the TTL values, and whether the session ID alone is enough for "same LLM".
- P8 (stats, PJ 2026-11-06): count the retry in the stats from the first build, not afterwards. This is R3i widened to the shared stash. Per tool: `retryStashed` (a call went into the stash), `retryReplays` (a bare or `again` resend merged into a stash), `retryHits` and `retryFails` (the replayed call succeeded or failed again), `retryExpired` (a resend found a slot past its TTL), `retryInvalidated` (a stash cleared by an edit to the same file), `retryEmpty` (a resend arrived with nothing stashed). Take-up rate = `retryReplays` divided by `retryStashed` for the same tool, compared with the failure count of first attempts. Read-only replays are counted under their own key (`againReplays`) so a search replay does not inflate the take-up rate of edit retries. Add `viaRetry:true` to the fault-log record of a replayed call that fails again, so `get-failure-log` separates retries from first attempts, and show the counters in the stats panel and in `get-edit-stats` next to `fragmentCommits`. The keys must be added to the schemas in `lib/edit-stats.js` first (the three places in "Working on this project"), because `bump()` ignores a key that is not already a number in the schema and says nothing.
- Effect on the stages: if accepted, F1 (the `retryable` field) becomes how a write tool says "stash this failure" and generates the nudge text, F2 and F3 become consumers of the shared stash, and R4k step 3 is built on the same stash (read-only class, `again:true` or a bare resend) instead of its own one-slot memory. Prove it on `insert` (write) and `grep-file` (read-only) first, then widen. It changes the framework, so it needs tests first, a full Pulsar restart and live probes.

## 7. Ideas and design questions (not designed)

- **Stacking anchors.** `resolveScope()` is a strict if/else-if ladder: the first hint present wins and the rest are silently ignored, so `{inFunction:'hal_init', afterString:'g_hal ='}` applies only `inFunction`. Proposal: resolve a primary scope, then apply a secondary content hint inside that window (two-stage `resolveScope()`). Open: which hint pairs may stack, every tool or opt-in per tool, and how failures distinguish "found outside the narrowed sub-scope but inside the outer one" from "not found at all".
- **`lineOffset` for `insert`.** An optional modifier that resolves a content anchor the normal way, then shifts N lines before inserting, so a blank or low-content target line a fixed distance from a unique anchor can be reached without raw line numbers. Open: interaction with `betweenHint`/scoped anchors, and whether negative offsets are allowed.
- **Per-tool `SUPPORTED_HINTS` declaration.** Every tool's schema currently accepts every hint in `ANCHOR_SCHEMA` / `STRUCTURAL_ANCHOR_SCHEMA` whether or not its handler understands it. Declare supported hints per tool, reject or warn on unsupported ones, and show only supported hints in each tool description. Low urgency; a later consolidation pass.
- **Per-tool capability tickboxes.** `features:{...}` today gates only cross-cutting concerns (dryRun, lint, ...). Open: the shape of a config that also gates which primitive operations a tool exposes.
- **Canonical parameter names.** The "string(s) to match" concept currently has five names across tools: `old_str`/`new_str` (match and replace), `afterContent`/`beforeContent` (match then position), `expectedContent` (verify only), `startContent`/`endContent` (a pair = a range), `matchString` (match then delete). Open: should match-and-replace share a name with match-only cases, is the start/end pair the same concept, and how to migrate without breaking callers. Needs its own design pass; related to the typed-anchor hint redesign (the "string" versus "content" hint names).
- **Gaps versus other AI code editors (no work planned):** plan mode, per-step approval, context-window indicator, automatic context compaction, parallel agents, browser access.

- [x] **XW1** (done 2026-11-19: matching was already tolerant; end-of-file insert and row-ending bugs fixed) (HIGH) `replace`, `insert` and `delete` should match anchors regardless of CR or LF differences, and write new text in the line ending of the surrounding lines. ### Code mode (idea, not approved)

- [ ] **XW22** (MEDIUM, design first; written 2026-11-18, nothing decided) Code mode: the model writes a short JavaScript program that makes several tool calls in one step, filters large results inside the program and returns only what is needed. Two references: (a) opencode, `reference-sources\opencode-dev\packages\codemode` (one `execute` tool, an owned interpreter built on Acorn with no `eval`, 8 parallel tool calls at most, host-set limits `timeoutMs`, `maxToolCalls` and `maxOutputBytes`, schema-described tools, see `codemode.md` and `README.md` there) and its adapter `packages\opencode\src\tool\code-mode.ts` (nested MCP calls still run the before and after hooks); (b) Claude Code's own experimental Code Mode (environment variable `CLAUDE_CODE_EXPERIMENTAL_CODE_MODE=1`, version 2.1.323 or later per the public docs; the docs were only skimmed). Why it fits this server: the pain in the XboxWirelessAdapter test was many round trips (search, edit, check), large outputs read whole, and hand-written PowerShell scripts doing what a program of tool calls would do. Costs and risks: a real sandbox is needed (Node `vm` is not a security boundary; opencode's runtime alone is about 141 KB; alternatives are `isolated-vm` or QuickJS); nested calls MUST go through the same gates as direct calls (the destructive-command prompt of `run-command`, `delete`, dry runs), or code mode becomes a way around them; stats, checkpoints and undo must attribute nested calls correctly. Suggested order: (1) XW1, XW11 and XW12 first, they remove most of what the scripts did by hand; (2) a simple `batch` tool that runs a list of tool calls in order and returns each result, with no interpreter and no new security surface; (3) try Claude Code's native Code Mode against this server and note what is still missing (if it already exposes MCP tools to the generated JavaScript, the server mainly needs well-formed, bounded, preferably structured output); (4) only then consider a built-in `execute` with a confined interpreter, for clients that have no native code mode.

## Explicitly out of scope

- Merging the fragment and whole-line modes of `replace` into one code path.
- Changing `replace-all` behaviour or defaults (the one accepted change: an empty query or substitution pattern is refused).
- One pure module per tool (the design is one module per concern).
- Removing a tool just because its usage stats are low. Tools other than the old `str_replace` were under-invested, not redundant; improve first, then measure.
