## Working on this project

- **Restarts:** every edit to a `lib/*.js` file (and the panel code in `lib/pulsar-edit-mcp-server.js`) needs a full Pulsar restart. There is no hot reload. `package.json` changes need a package reload. A brand-new standalone file needs nothing until something requires it. Tool registration or schema changes are only picked up by a new MCP session.
- **Method:** one change at a time. Write the test first (see it fail, then pass), run `npm test`, restart Pulsar, then verify live with a real tool call before calling anything done. Prove a change on one tool before widening it to the others.
- **New tool or new stats key:** it must be added in three places or its counts silently vanish: the `editStats` initialiser and the `TOOL_REGISTRY` in `lib/edit-stats.js`, and a key in `GROUP_DEFS` in `lib/pulsar-edit-mcp-server.js`. `bump()` on a key that is not in the schema is a silent no-op.
- **Renaming or consolidating a tool:** grep `lib/*.js` for the old name as a string literal and as a table key. Keyed lookups fail silently.
- **Changelog:** add an entry to the top of CHANGELOG.md for every behaviour change.

### Design rules (settled, do not reopen without a strong reason)

- Engine defaults must be safe for destructive callers. Permissive behaviour is opt-in (for example `delete` opts out of `autoRescue`).
- An ambiguous match with no `occurrence` is refused, never guessed.
- `occurrence` counts matches from 1 and must be a whole number. An out-of-range value is refused, never clamped.
- Part-line editing exists only as `replace` with `fragment:true` (one line or a multi-line span that may start and end mid-line, since 2026-10-17), guarded by `lib/identifier-boundary.js`. The guard refuses (does not just warn); `guardIdentifier:false` is the escape hatch.
- Regex exists only in `sed` and in the search tools (`find-text`, `grep-file`, `grep-project`, `search-functions`); the edit tools take literal text only (R2a, closed 2026-10-30).
- Failure counters are tallied in parallel on purpose: a failure lands in the shared diagnosis key and in the tool's own key. All hints for all tools must be logged, and a match failure records the diff, the buffer text and the proposed text.
- Tools keep distinct, separately described names; only the implementation is shared. Do not collapse the tool surface into mega-tools with a mode parameter, and do not leave aliases for retired tools.

- [ ] **R2h** (MEDIUM) Every edit tool silently destroys bytes that are not valid UTF-8. ### R4 - `sed` as a JS implementation of GNU sed (decided by PJ 2026-10-18; the tool is done and live; R4g is MEDIUM, the other open items are LOW)
Goal: the `sed` tool behaves exactly like GNU sed 4.9: the same script syntax, POSIX BRE/ERE regex with leftmost-longest matching, replacement with `\1` and `&` (a literal `$` stays literal), and the same commands and addresses. Status: R4a to R4d are done and the tool has run real sed scripts since 2026-10-24 (see CHANGELOG.md); the old JS-regex subset (`lib/sed-plan.js`) was deleted on 2026-10-25. `sed` is the part-line regex tool, so the fragment-mode regex of R2a is not built (R2a keeps only its guard).

- Decisions: our own implementation in pure modules, no sed binary needed at runtime: `lib/posix-regex.js` (BRE and ERE with the GNU extensions, own matcher), `lib/sed-parse.js` (script parser), `lib/sed-run.js` (interpreter over a lines array). The test oracle is real GNU sed 4.9: Linux sed in the assistant's sandbox generates golden outputs, which the tests in `test/` embed and run in plain node; PJ's Windows sed 4.9 (`test/sed-oracle/sed.exe`, not part of the package) runs the differential checks (`test/sed-oracle/run-diff.js`).
- Never implemented: `e` (shell exec). Off by default behind a future capability gate: `w`, `W`, `r`, `R` (file I/O).
- Known tail risk, stated up front: POSIX submatch rules for highly ambiguous patterns. Differential tests measure it and every remaining deviation is listed in the CHANGELOG.
- Decided (2026-10-21 to 2026-10-24): exact GNU sed 4.9 semantics with no extra guards (a `sed -n -i` style script may empty the file, as real sed does); `dryRun` stays as the tool's own preview; the old engine was replaced outright, with no fallback; `occurrence` is only the picker for an ambiguous scope hint (`s///N` stays in the script); `w W r R e` are refused by the parser sandbox.

## 2. Failure handling and retry

**Why:** failures are frequent and each one makes the caller resend the whole call to fix one field. The commonest case is an ambiguous anchor, where the failure already lists the candidate lines and the fix is a single integer (`occurrence:N`).

**What exists:** `features.retryOnFail` in `lib/tool-framework.js` (stashes a failed call and merges one named field into a bare retry) plus `RETRY_FIELD_BY_TOOL` / `retryNudge()` in `lib/match-engine.js`. It works end to end with both relative and absolute paths, but only `str_replace` and `replace` have it registered.

**Known inconsistencies:**
- Tools signal failure with five different flags (`matched:false`, `inserted:false`, `deleted:false`, `found:false`, `applied:false`), and some `deleted:false` / `applied:false` results are dry-run previews rather than failures. The framework can only stash on `matched:false`.
- `RETRY_FIELD_BY_TOOL` lists `delete`, `replace-block` and `replace-function-body`, but none of them has `retryOnFail` registered. Their "not found" messages can therefore advertise a bare retry the framework does not support (it works only as a fresh, complete call). `delete`'s Mode 4 paths already omit the nudge on purpose.

**Principles:** prove on one tool, restart, verify live, then widen. Unadvertised capability goes unused, so the failure text itself must say how to retry cheaply. Only retryable failures stash (a bad path or missing argument must not). Keep `matched:false` working alongside any new signal.

**Decisions already made:**
- A: a retry may supply any single anchor key and it replaces whichever anchor the original call used. A retry supplying two anchor keys is rejected.
- B: the new `retryable` signal is additive. The framework stashes on `retryable` or on the legacy `matched:false` path; `retryable` wins if both are present.
- C: occurrence retry is one-shot and only valid right after an ambiguity failure on the same file. With nothing pending, `{filePath, occurrence}` falls through to the normal ambiguity refusal.

### Stages

- [ ] **F1 - Stage 1.** Add an optional `retryable` field to failure responses, e.g. `{kind:'occurrence', candidates:[4,8,12]}` or `{kind:'field', field:'afterString'}`. The framework stashes on it and generates the nudge text from `kind`, so wording lives in one place. Exit: a synthetic `retryable` result stashes, expires on a same-file commit, and never stashes for a non-retryable failure. Needs maintainer approval of the kind-only shape before starting.
- [ ] **F2 - Stage 2 (highest value).** Occurrence retry: `{filePath, occurrence:N}` merges into the stashed args. Wire the shared `buildFailResponse()` / `ambiguityCheck()` path first (covers `insert`, `delete`, `replace-block`, `replace-function-body`), then `insert`'s bespoke `sectionHint`/`preprocBlock` ambiguity. Validate `N` against the candidate list. Exit, on `insert` first: an ambiguous `afterString` followed by `{filePath, occurrence:2}` lands at the second match, and a fresh ambiguous call with no `occurrence` still refuses.
- [ ] **F3 - Stage 3.** "Not found" correction retry, generalising `retryOnFail.field` to whichever anchor key the stashed call used. Order: `insert`, `delete`, `replace-block`, `replace-function-body` (`replace` already has this, since 2026-10-17). For `insert`, make `new_str` optional-with-guard (same pattern as `commitLastPreview`); expect the same Zod-transport gotcha for any other required field a retry omits. Prove on `insert` alone before moving on.
- [ ] **F4 - Stage 4.** Error-string audit, done per tool as each stage reaches it. Known issues (not re-tested live on 2026-10-16):
  - (Found 2026-10-17.) `replace` lacks two `str_replace` extras: the "old_str looks like a complete function, use replace-function-body" nudge, and the named tool suggestions in the consecutive-failure line (`replace` only says "a different editing tool").
  - (Found 2026-10-17, shared.) The "Closest area found" window for a COMMENT MISMATCH failure can sit away from the target: the window showed lines 1 to 6 while the target was line 7.

**Out of scope for this plan:** extending retry to `sed`, `apply-patch` or `read` before stages F1-F3 pass on `insert`; moving `apply-patch`'s `confirm` + `patchRescueStore` onto `resendlessCommit`; the hint-naming cleanup (see "Canonical parameter names" in section 7).

## 7. Ideas and design questions (not designed)

- **Stacking anchors.** `resolveScope()` is a strict if/else-if ladder: the first hint present wins and the rest are silently ignored, so `{inFunction:'hal_init', afterString:'g_hal ='}` applies only `inFunction`. Proposal: resolve a primary scope, then apply a secondary content hint inside that window (two-stage `resolveScope()`). Open: which hint pairs may stack, every tool or opt-in per tool, and how failures distinguish "found outside the narrowed sub-scope but inside the outer one" from "not found at all".
- **`lineOffset` for `insert`.** An optional modifier that resolves a content anchor the normal way, then shifts N lines before inserting, so a blank or low-content target line a fixed distance from a unique anchor can be reached without raw line numbers. Open: interaction with `betweenHint`/scoped anchors, and whether negative offsets are allowed.
- **Per-tool `SUPPORTED_HINTS` declaration.** Every tool's schema currently accepts every hint in `ANCHOR_SCHEMA` / `STRUCTURAL_ANCHOR_SCHEMA` whether or not its handler understands it. Declare supported hints per tool, reject or warn on unsupported ones, and show only supported hints in each tool description. Low urgency; a later consolidation pass.
- **Per-tool capability tickboxes.** `features:{...}` today gates only cross-cutting concerns (dryRun, lint, ...). Open: the shape of a config that also gates which primitive operations a tool exposes.
- **Canonical parameter names.** The "string(s) to match" concept currently has five names across tools: `old_str`/`new_str` (match and replace), `afterContent`/`beforeContent` (match then position), `expectedContent` (verify only), `startContent`/`endContent` (a pair = a range), `matchString` (match then delete). Open: should match-and-replace share a name with match-only cases, is the start/end pair the same concept, and how to migrate without breaking callers. Needs its own design pass; related to the typed-anchor hint redesign (the "string" versus "content" hint names).
- **Gaps versus other AI code editors (no work planned):** plan mode, per-step approval, context-window indicator, automatic context compaction, parallel agents, browser access.
